Scope, assumptions & access note

This spec covers the five editor changes you listed. It assumes the app stays on its current stack: three.js / WebGL front end, Vite build, Vercel serverless backend, with accounts, orders, payments, admin and in-house production already live.

Access note: the app source lives in a separate GitHub repo not reachable from this session (scoped to disburyben/docs). This document is therefore the deliverable; when you want me to implement, grant access to that repo (or move/copy the source) and I'll code against it.
The single most important change is #5. If the editor currently flattens a design to one PNG, your paint team cannot break it down. Everything in #2–#4 should be built on top of the structured DesignDocument so that #5 — a faithful, per-layer, Pantone-coded spec sheet — falls out for free. Design the data model first, UI second.

Assumptions to confirm

  • Each helmet shell is a glTF model with a single, sane UV unwrap (or can be re-unwrapped). Region masking (#4) depends on this.
  • "Save Design" currently persists something — confirm whether it stores structured layer data or a flattened image/screenshot. This determines how much of #5 is new vs. refactor.
  • The Spec Sheet PDF is generated client-side (e.g. jsPDF/pdf-lib) or server-side. Recommendation: server-side render for consistency and to attach production assets.

The backbone: DesignDocument data model

Everything serializes to one JSON document. The 3D view, the editable layer panel, the saved design, and the paint-team spec sheet are all projections of this object. Store it as JSONB in your DB and as the canonical save format.

// ---- Canonical design document (TypeScript-style) ----
interface DesignDocument {
  id: string;
  schemaVersion: "1.0";
  helmet: {
    modelId: string;           // e.g. "arai-gp7"
    brand: string; model: string; size?: string;
    shellGltfUrl: string;      // the 3D asset used
    uvSet: string;             // which UV unwrap regions reference
  };
  finishDefault: Finish;       // base shell finish
  regions: Region[];           // painted zones (#4)
  layers: Layer[];             // ordered bottom→top (#3)
  meta: { createdBy: string; createdAt: string; updatedAt: string;
          orderId?: string; status: "draft"|"submitted"|"in_production"|"done"; };
}

type Finish = { type: "gloss"|"matte"|"satin"|"metallic"|"carbon"|"chrome"|"candy"|"pearl";
                clearcoat?: number; flakeSize?: number; };

interface ColorSpec {                // EVERY colour carries production codes
  hex: string;                          // screen value
  pantone?: string; ral?: string;       // what painters actually mix
  name?: string; finish?: Finish;
}

interface Region {                     // a paintable area of the shell (#4)
  id: string; name: string;             // "Shell", "Chin bar", "Vents", "Visor trim"
  maskTextureUrl: string;               // grayscale mask in UV space
  fill: ColorSpec | Gradient;
}

interface Layer {                      // artwork/decal/text/shape (#2,#3)
  id: string; name: string;
  type: "image"|"text"|"shape"|"aiTexture";
  visible: boolean; locked: boolean; opacity: number; blend: BlendMode;
  z: number;                            // explicit z-order
  groupId?: string;
  source: { assetUrl?: string; text?: string; font?: string; color?: ColorSpec;
            originalUploadUrl?: string; };   // keep the raw upload for the paint team
  placement: Placement;                 // see #2
}

interface Placement {                  // UV-space transform = stable & printable
  space: "uv"|"decal";
  uv?: { x:number; y:number; w:number; h:number; rotation:number; };   // normalized 0..1
  decal?: { position:[number,number,number]; orientation:[number,number,number];
            size:[number,number,number]; };  // three.js DecalGeometry params
}
Why UV-space placement matters: storing each layer's transform in normalized UV coordinates (not just as a baked pixel) means the same document can drive (a) the live 3D view, (b) a flat per-view production layout, and (c) re-editing later — without ever flattening. This is the hinge that makes #5 possible.

#1 — Remove preset designs, replace the entry point Low effort

Problem

The current bundle ships a "wrap-design picker (Tier C)" with .design-thumb preset thumbnails and a canned decal set — filler that cheapens first impression.

Change

  • Remove the preset wrap-design strip and the placeholder decal presets from the UI and the asset manifest.
  • Replace the empty state with a deliberate "Start" chooser: Start blank Upload your design Pick a real template. Don't drop users into a blank shell with no guidance.
  • Keep a curated template slot for later — but only populate it with genuine racing liveries built on the new DesignDocument format, so a "template" is just a starter document the user can fully edit.

Acceptance criteria

  • No placeholder/preset designs appear anywhere in the editor or shipped assets.
  • First-run shows the Start chooser; each path loads a valid empty/started DesignDocument.
  • Removing presets does not break save/load of existing customer designs (migration: ignore unknown preset refs).

#2 — Move / resize / rotate artwork High effort — biggest UX win

Problem

Placement is "click to place" via DecalGeometry; moving/resizing is clumsy and decals stretch on compound curves (crown, chin).

Target behaviour

  • Direct manipulation on the shell: drag to move, scroll/pinch to scale, on-surface rotate ring. Live bounding box + handles.
  • Snapping & guides: center line of the shell, mirror across the centerline, equal-spacing guides, numeric nudge.
  • Two placement modes (store which in Placement.space):
    • Decal mode — small artwork/logos: keep DecalGeometry (raycast hit → position/orientation/size). Good for stickers; bad for full liveries. [1]
    • UV mode — large artwork/liveries: edit on a flattened 2D UV layout of the shell, then render via the texture. Eliminates the stretching that plagues decals on curved panels. [2]
  • Undo/redo (command stack over the DesignDocument), and full touch support (drag/pinch/rotate gestures).

Implementation notes

  • Raycast from pointer → mesh → barycentric → UV coordinate; that UV is the layer's placement.uv anchor. [2]
  • Render the editable layer stack to an offscreen canvas/texture in UV space, then apply as the shell's map/decal — so manipulation is 2D math (cheap, exact) while the result shows in 3D.
  • Provide a toggle: "Edit on 3D" vs "Edit on flat layout" — power users and your paint team will want the flat view.

Acceptance criteria

  • A user can place artwork, then move/scale/rotate it smoothly with mouse and touch, with visible handles and snapping.
  • Large artwork in UV mode shows no visible stretching across crown/chin vs. current decal behaviour.
  • Every transform persists to placement and survives save → reload identically.
  • Undo/redo covers move, scale, rotate, add, delete.

#3 — Layer system rework Medium effort

Problem

Layer primitives exist (.layer-card) but the model/operations are limited.

Target behaviour

Per-layer controls

  • Drag-to-reorder (z-order), show/hide, lock, rename, duplicate, delete.
  • Opacity slider + blend mode (normal, multiply, screen, overlay).
  • Thumbnail preview per layer; selected-layer highlight synced with the 3D view.

Structure

  • Groups/folders (sponsor pack, base livery, numbers).
  • Layer types: image · text · shape · aiTexture (future).
  • Multi-select + group transform.

Implementation notes

  • Layer panel is a pure view over DesignDocument.layers sorted by z; all ops mutate the document then re-render.
  • Compositing: render layers bottom→top into the UV texture honoring opacity + blend; cache unchanged layers for performance.
  • Keep source.originalUploadUrl for every image layer — the paint team needs the raw file, not just the composited result.

Acceptance criteria

  • Reordering layers visibly changes overlap order in 3D; opacity/blend apply live.
  • Hide/lock/rename/duplicate/group all persist and round-trip through save.
  • Selecting a layer in the panel highlights it in the 3D view and vice-versa.

#4 — Colours & colour regions Medium–High effort

Problem

Colour is applied broadly; there's no concept of discrete paintable areas, and colours are hex-only (useless to a painter).

Target behaviour

  • Defined regions/zones per shell (Shell, Chin bar, Top vents, Side pods, Rear spoiler, Visor trim, Edge trim) — each a grayscale UV mask baked once per model. Tapping a region selects it; colour/finish applies only there.
  • Per-region finish (gloss/matte/metallic/carbon/candy…) independent of colour.
  • Gradients and a per-design palette (saved swatches, reusable).
  • Brand/sponsor colours library; eyedropper from an uploaded image.
  • Pantone/RAL mapping required: every colour stores {hex, pantone?, ral?}. Offer a "nearest Pantone" suggestion on pick; let the user override. This is the data your painters mix from.

Implementation notes

  • Region masks live in Region.maskTextureUrl; the shader/compositor multiplies fill colour by mask to confine paint to the zone.
  • Authoring masks: one-time per shell in Blender/Substance (paint material IDs → export masks), or an in-app "magic-wand by UV island" helper later.
  • Nearest-Pantone: small lookup table (sRGB→Pantone Coated) client-side; flag that screen colour ≠ mixed paint and that final sign-off is on the physical proof.

Acceptance criteria

  • User can select a named region and recolour only that area; adjacent regions unaffected.
  • Each region carries an independent finish.
  • Every colour in the document has a hex and an assigned/overridable Pantone (or RAL) code.
  • Palette swatches and eyedropper work and persist.

#5 — Structured save & paint-team spec sheet Critical / production

Problem (the one that matters)

If "Save Design" stores a flattened image, your paint team can't break the design down into mixable colours, placeable artwork, and per-panel instructions. The save must be the structured DesignDocument, and the spec sheet must enumerate it.

Save behaviour

  • Persist the full DesignDocument JSON (DB JSONB + versioned). Never store only a screenshot.
  • Store all source assets (each layer's originalUploadUrl + composited region masks) in Blob/R2 with the order.
  • On submit/checkout, snapshot an immutable copy tied to the orderId so later edits don't mutate a design already in production.

Spec sheet (PDF) — what the paint team receives

SectionContents
HeaderOrder id, customer, helmet brand/model/size, shell glTF id, base finish, date, status.
5-view rendersLeft, right, front, back, top — high-res renders of the final 3D design.
Flat layoutThe UV-flattened livery (the "unwrapped" paint map) with layer outlines — what gets masked/sprayed.
Colour scheduleTable of every colour: swatch · hex · Pantone/RAL · finish · which region(s) it fills.
Layer breakdownOrdered list: each layer's name, type, thumbnail, blend/opacity, and placement (region or UV coords + size + rotation), with a link to the raw source asset.

Implementation notes

  • Generate the sheet server-side (a Vercel function renders the 5 views via headless three.js / stored render targets, fills a PDF template with the colour schedule + layer table, bundles assets into a zip). Keeps output consistent and lets you attach files the browser can't.
  • The colour schedule and layer table are direct serializations of the DesignDocument — no manual authoring. That's the payoff of building #2–#4 on the shared model.
  • Give the paint team an admin view of the same breakdown (live, not just PDF) tied to the order/job dashboard you already have.

Acceptance criteria

  • Saved design reloads byte-for-byte identical (all layers/regions/colours/transforms intact).
  • Spec sheet lists every colour with a Pantone/RAL code and every layer with placement + source asset link.
  • Paint team can reproduce the design from the sheet alone — no guessing, no flattened-image reverse-engineering.
  • An order in production is immutable against later customer edits.
