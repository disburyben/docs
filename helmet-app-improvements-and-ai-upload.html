Where you stand

From the competitor research: you already have the rare full stack — a real-time three.js 3D editor (Layers, decals, finishes, PDF/PNG export) plus commerce (accounts, orders, payments, admin) plus in-house production. Only Helmade matches that combination, and theirs took an agency + a 3D studio + Magento to build.

That means the next wins are not "catch up on basics." They are: (1) visual realism to reach the Helmade/VELDT tier, (2) a signature differentiator no competitor has — which is exactly your AI design-upload idea, and (3) distribution (traffic/brand). This doc focuses on (1) and (2), the parts you control with code.

Technology to implement

Rendering / three.js

  • MeshPhysicalMaterial — clearcoat (gloss lacquer), iridescence (candy/pearl), sheen, metalness/roughness maps, anisotropy (brushed metal).
  • HDRI IBL: RGBELoader/EXRLoader + PMREMGenerator for real reflections; ACESFilmicToneMapping.
  • Post-processing: subtle bloom, SSAO, optional screen-space reflections.
  • DecalGeometry for sticker/logo placement on curved shells; raycast-to-UV for paint-where-you-click. [2]
  • Render targets to output depth / normal / edge maps of the live view — the key input for the AI feature (§05).

Assets & performance

  • glTF + Draco or meshopt geometry compression.
  • KTX2 / Basis GPU-compressed textures (smaller, faster upload).
  • LOD + lazy-load shells; cache via CDN.

AI services (no GPU on Vercel — call out to these)

  • Replicate / fal.ai / Stability API — hosted SDXL + ControlNet, pay-per-call.
  • Meshy / 3D AI Studio — AI texture-from-image APIs that auto-handle UV/projection. [3]
  • SAM (segment), rembg (bg removal), OpenCV.js (perspective de-warp), Real-ESRGAN (upscale), potrace/vectorizer (vectorize line art).

★ "Upload Your Design" — the flagship AI feature

The pitch: a customer photographs a napkin sketch, a kid's drawing, an old helmet, or uploads a flat 2D concept — and your app regenerates that design as a real livery on their chosen 3D helmet, orbitable, editable, and ready to order & produce in-house. No competitor in the research offers this; the closest (Pixelcut/OpenArt) generate a pretty 2D image that can't be mapped to a real shell or manufactured. [4]

Why this is your moat: AI generators make images; design studios make files by hand. You'd be the only one turning an untrained customer's rough idea into a precise, editable, manufacturable 3D livery — and you already own the production line to make it real.

What "upload" needs to handle

  • A photo of paper (perspective-skewed, shadows, background clutter) → detect, de-warp, clean.
  • A flat digital concept (PNG/JPG/PDF) → use directly as a design source.
  • A photo of an existing helmet → understand it's already a 3D object; extract the livery.
  • A rough sketch ("blue with lightning + my number 7") → interpret intent, generate a polished version.

Approach B · AI re-render with geometry control Phase 2

The "wow" version. Render your 3D helmet's depth/edge maps from the current camera, then use ControlNet + img2img so a diffusion model repaints the helmet using the uploaded design's colors/motifs/style — constrained to the actual helmet geometry. This is exactly how tools like StableProjectorz work (ControlNet Depth + img2img inpaint into masked areas). [5]

Approach C · AI texture bake onto the real UV Phase 3 / endgame

The true-3D version: generate a full UV texture map for the helmet from the reference image, baked for multi-view consistency, applied as the model's albedo so it's fully orbitable, editable in your Layers, and exportable to your production sheet. Off-the-shelf APIs (Meshy, 3D AI Studio) auto-handle UV/seams/texel density from a reference photo; research methods (Make-A-Texture, TexGen, FlexPainter, Meta 3D TextureGen) do depth-aware multi-view diffusion if you self-host later. Infrastructure on your stack

Key constraint: GPU diffusion cannot run inside Vercel serverless functions (no GPU, short timeouts). Your Vercel function should be the orchestrator, not the model host.
  • Storage: uploads + generated outputs in Vercel Blob, Cloudflare R2, or S3 (you have Cloudflare available). Never inline large images through functions.
  • Async jobs: diffusion takes seconds–minutes > function timeout. Pattern: function creates a job → calls GPU API (Replicate/fal.ai/Meshy) → returns a job id → client polls or you receive a webhook → store result → notify via your existing admin/notification system.
  • GPU compute options (managed → self-hosted): Replicate / fal.ai / Stability (easiest, per-call) → Modal / RunPod (your own ControlNet pipeline) → dedicated GPU box (cheapest at scale, most ops).
  • Queue: a lightweight queue (Cloudflare Queues, Upstash QStash, or a DB table) to manage concurrency & retries.
  • Caching: hash uploads to dedupe; cache cleaned images so re-renders are cheap.

Risks: IP, moderation, cost

  • Copyright / trademarks: customers will upload F1 team liveries, brand logos, characters. Decide policy (allow sponsor logos the racer owns rights to; flag obvious IP). Add a terms checkbox asserting they have rights. This is a real liability since you manufacture the physical product.
  • Content moderation: run an automated NSFW / unsafe-content filter on uploads before they hit production (hosted moderation APIs or an open model).
  • Cost control: generative calls cost real money (cents–dimes each). Gate AI generation behind your paid/checkout flow or a small credit system; keep Approach A (cheap) free as the funnel.
  • Quality gate: AI output should be a proposal a human approves before it enters your production queue — protects your in-house paint/print step from garbage-in.
  • Latency UX: show a progress state + let users keep editing while a render runs; never block the editor.
